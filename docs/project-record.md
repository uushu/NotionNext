## 固定防再犯规则

### Notion 内容发布

1. 修改现有文章后，不默认承诺“立刻显示”。先请求正式文章 URL；只有仍是旧内容时才执行刷新或重部署。
2. 新建并发布文章后，必须确认新页面已经进入生产数据。若路由未生成，重新部署当前 `main`，使构建重新读取 Notion。
3. 重部署不能只看 `READY`。正式上线必须同时满足：
   - 正式文章 URL 返回 `200`；
   - 真实浏览器能看到正确标题和正文；
   - 首页或文章列表已经收录。
4. 若出现 404 或旧内容，按“构建数据 → ISR/Data → CDN → 浏览器”逐层定位；不得把带查询参数的成功请求当作干净 URL 已修复。
5. Notion 写入或更新后必须完整回读正文和属性，重点检查行内代码、加粗、链接、代码块、Slug、状态和日期。

### Contribution 热力图

1. 同一文章同一天只计 1 次，保留当天最后一次事件；不同文章分别计数。
2. 不再把文章显示日期、Notion 系统最后编辑时间和 Contribution 事件时间混称为“最终修改日期”。
3. 在 Contribution 时间口径修复前，向用户明确说明：今天实际编辑 Notion 页面，即使把文章显示日期改成昨天，Notion 的系统 `last_edited_time` 仍是今天，热力图仍可能记录今天。
4. 后续修复必须先冻结规则：
   - 热力图究竟按“真实操作时间”还是“文章属性日期”计数；
   - 站点统一使用哪个 IANA 时区。
5. 时区必须显式配置并在服务端、客户端、测试中使用同一日期函数；不得继续依赖服务器或浏览器的默认时区。
6. 回归测试至少覆盖：同篇同日、同篇跨日、不同文章同日、UTC 跨日、修改显示日期但系统编辑时间为今天。

### 写作与项目协作

1. 博客文章自然直接，标题简短；保留具体步骤、参数和排错证据，删除套话、抽象包装和重复总结。
2. Skill、命令、文件名使用准确名称，但不围绕术语反复说教。
3. 项目事实必须区分“计划、已执行、已验证、已上线”；任何状态只能由对应证据支持。
4. 代码修改只进入 `v1`，Preview 验收稳定后再合并 `main`；项目记录不写进 README。
